# Auditoria do BuildMaster — 6 de outubro de 2026

O problema principal ocorre no caminho entre a leitura do print e a geração
da ficha. O Reader V2 é o leitor padrão, mas a conclusão da leitura não abria
a seção da conferência. Além disso, o formulário sumia antes de a geração
assíncrona terminar. A correção acompanha todo esse caminho, incluindo os
dados que efetivamente chegam ao motor e o histórico salvo.

Base examinada: `main`, commit `8a81d617c4cc1a57ece0c4661afe9612c2546ab4`,
versão de produto `40.80.0`. Esse número, sozinho, não identifica o APK
instalado: diferentes commits podem publicar a mesma versão de produto.

## Defeitos reproduzidos e correções

| Área | Defeito observado | Comportamento corrigido |
|---|---|---|
| Navegação | OCR concluía, mas permanecia no Leitor | Abre a seção Resultado com os dados para conferência |
| Nome e estilo | PSM de linha única destruía o nome na zona com duas linhas | Lê o bloco e separa nome e estilo reconhecido |
| Modo automático | Usava regiões diferentes do layout de calibração padrão | Reutiliza as regiões canônicas do mesmo layout |
| Atributos | Contar 26 números não preservava sua associação aos atributos | Só aceita ordem comprovada nas três colunas, 10 + 9 + 7 |
| Identidade e PP | Campos vazios da nova carta podiam herdar valores anteriores | Cada print começa com sua própria evidência |
| Habilidades e ímpeto | A conferência perdia habilidades reconhecidas | Preserva nomes canônicos e evidencia leituras ambíguas |
| Cancelamento | Uma leitura atrasada podia reabrir a conferência após cancelar | Invalida a tentativa e interrompe reconhecimentos pendentes |
| Geração | A confirmação era removida antes de conhecer o resultado | Aguarda o resultado e conserva correções para revisão/tentativa |
| Conferência | Atributos apagados/corrigidos e habilidades removidas reapareciam do OCR original | Os valores confirmados têm autoridade; metadados da edição permanecem preservados |
| Troca de carta | Uma confirmação antiga podia descartar a próxima imagem, inclusive vindo do modo manual | Captura contexto antes da importação e revalida geração, seleção e conta durante a finalização |
| Treino | PP confiável autorizava receita genérica com atributos ausentes | Exige atributos reais; cobertura parcial permanece provisória |
| Certificação | Contagem declarada do OCR podia certificar atributos inexistentes | Certificação completa exige os 26 valores reais e a identidade confiável |
| Pesquisa | Fonte de outro patch/edição podia influenciar a decisão | Confere identidade, patch, confiança e conflitos antes de aplicar influência |
| Histórico | Limpeza por falta de espaço removia dados que podiam ser a única cópia | Remove apenas caches regeneráveis |
| Nuvem | Excluir a última carta removia também a linha com outros backups | Sincroniza a lista vazia e preserva outras seções/pontos de restauração |
| Isolamento de conta | Operações atrasadas podiam gravar credenciais, histórico, galeria ou aprendizado na conta seguinte | Fixa a conta antes de filas/awaits e verifica commits, fallback, rollback, limpeza e sincronização |
| Preparação de build | Convergências antigas rejeitavam ou substituíam o novo gravador protegido | Preserva as guardas e os contratos transacionais de forma idempotente |
| Sessão offline | Refresh rejeitado retirava a identidade usada pelo armazenamento local | Remove credenciais remotas e preserva a identidade do workspace offline |
| CI | O novo leitor não participava dos gates principais | Leitor e auditoria bloqueiam APK/AAB/PR; navegador e WASM real entram no PR e R542/main |

## Método de ficha por carta

A identidade da edição, os valores realmente lidos, os pontos disponíveis,
a posição natural, a posição de uso, as habilidades possuídas e o contexto
tático continuam separados. A posição de uso pode ser adaptada sem reescrever
a identidade da carta. Estilo inativo precisa aparecer como tal.

Relatos de comunidade só influenciam a decisão quando foram associados à
edição e ao patch corretos, têm confiança suficiente e não possuem conflito.
Fontes antigas ou sem edição permanecem disponíveis para revisão. Uma
etiqueta global de confiança não promove uma fonte fraca.

O motor não deve criar diferenças artificiais só para cada atacante ter
uma receita diferente. A regressão com Massaro, Van Basten e Drogba usa
cartas distintas com o mesmo orçamento. Os dois primeiros podem obter a
mesma distribuição, enquanto Drogba obtém outra; as habilidades respeitam
as habilidades possuídas em cada carta. Isso verifica decisões por dados,
em vez de uma receita única por posição ou de uma receita por nome.

Dados incompletos não justificam a promessa de "melhor ficha". Para jogadores
de linha, o mínimo crítico é 10 atributos reais; para goleiros, 4. A ficha
parcial útil requer aceite e fica marcada como provisória. A certificação
final exige todos os 26 atributos e os demais requisitos de identidade,
nível e orçamento. Isso não equivale a teste de gameplay no eFootball.

## Verificação reproduzível

```bash
npm ci
npm run test:reader
npm run test:audit
npx playwright install --with-deps chromium
npm run vendor:ocr
npm run test:reader:browser
npm run typecheck
npm run test:all
npm run apk:build-web
npm run quality:bundle-built
```

Os testes de ações exercitam a facade real e controlam apenas a resposta
do OCR e a fronteira da geração. O teste de UI monta o componente React
de produção. O teste de navegador usa decodificação de imagem, canvas,
worker, idioma português e WASM locais reais. Sua imagem sintética tem
valores conhecidos e layout canônico; nenhuma API de IA remota é usada.
Ela não substitui os prints originais nem comprova toda variação de layout.

Resultados locais concluídos: 16 arquivos de regressão do leitor e quatro
configurações TypeScript; 15 arquivos de regressão da auditoria; revisão React
e OCR/WASM no Chromium; TypeScript oficial; 15 grupos do pré-voo de CI,
incluindo 127 verificações estruturais. A exportação web para Capacitor e o
build web também passaram. O bundle medido tem 261 chunks, 10.842.405 bytes
no total e 650.680 bytes no maior chunk.

A execução inicial de `test:all` não concluiu (saída 2 após R130); ela não é
registrada como sucesso integral. Os grupos R131–R200 foram retomados em
execução separada. Os gates remotos precisam corresponder ao SHA entregue.

O código TypeScript ganhou uma reserva de manutenção adicional de apenas
32 KiB, após medir a base de 6.049.637 bytes e a expansão das correções, incluindo
os gravadores e a finalização protegidos. O checkpoint útil é 6.094.848 bytes.
A reserva de 64 KiB continua obrigatória. Os limites do JavaScript compilado
continuam em 15 MiB no total e 5 MiB por chunk. Esses limites não medem o
heap de WASM, os bitmaps ou o consumo do WebView no aparelho.

Os detalhes dos gates, da exportação Capacitor e da confirmação física
estão em [reader-runtime/README.md](reader-runtime/README.md).

## Alcance e limites

Foram examinados os pontos de entrada, a cadeia ativa de OCR/geração,
as autoridades de evidência e progressão, os consumidores de scouting,
a persistência local/nuvem, a sessão e os workflows de build/release.
Verificações estruturais cobrem os demais módulos e rotas. Essa auditoria
não demonstra que cada funcionalidade ou cada linha do projeto esteja
correta em qualquer aparelho ou condição de rede.

O assistente existente é baseado em regras locais e não possui um provedor
multimodal remoto configurado. O reparo do OCR não depende de uma API paga.
Pesquisa automática na internet e conhecimento de gameplay validado no
jogo não devem ser apresentados como recursos já implementados.

Permanecem necessárias a compilação/instalação Android e a execução dos
prints originais no APK identificado pelo commit, versionCode e checksum,
além da confirmação do backend Supabase real. Os testes de conta e nuvem
usam dados isolados; não alteram contas ou backups do usuário.
